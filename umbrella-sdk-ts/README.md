# @umbrellaos/sdk

Generated TypeScript client for UmbrellaOS's public REST API. Phase 7
completion, Task A — read
`dispatches/PHASE7-COMPLETION/SUBCHAT-HANDOFF-PHASE7-COMPLETION.md` and
`PROJECT-PRINCIPLES-AND-WORKING-RULES.md` first if you haven't.

## What this is for

**External consumers of UmbrellaOS's public REST API** — someone
building a script, a bot, or a service outside this repo that wants to
call UmbrellaOS capabilities without hand-rolling `fetch` calls and
retyping the request/response shapes.

**This is explicitly not** a replacement for
`umbrella-dashboard-CURRENT/lib/api.ts` — the dashboard's own
hand-written fetch wrappers have grown real conventions (session-cookie
handling, `ApiError` typing) this generic SDK doesn't replicate, and
migrating the dashboard onto this package is a real, separate, riskier
piece of work explicitly out of scope for this dispatch (see the
dispatch doc's Task A, point 3). Flagged here as a future option, not
started.

## Install / build

```bash
npm install
npm run generate-types   # regenerate src/generated-types.ts from ./openapi.json
npm run build            # tsc -> dist/
npm run typecheck        # tsc --noEmit, no build output
```

`openapi.json` in this package's root is a snapshot generated by
`umbrella-core-CURRENT/scripts/export_openapi_schema.py` — regenerate it
from a current backend checkout before regenerating types:

```bash
cd umbrella-core-CURRENT
python scripts/export_openapi_schema.py --output ../umbrella-sdk-ts/openapi.json
cd ../umbrella-sdk-ts
npm run generate-types
```

## Usage

```typescript
import { UmbrellaClient } from "@umbrellaos/sdk";

const client = new UmbrellaClient({
  baseUrl: "https://umbrella.example.com",
  apiKey: process.env.UMBRELLA_API_KEY!, // scoped key from identity.apikey.create
});

// Introspection — same schema the CLI and (Phase 5) AI Tool Registry adapters use.
const capabilities = await client.listCapabilities();

// Invoke any registered capability by name — this is the entire public
// REST surface (see registry/adapters/rest.py in umbrella-core):
// every capability, current and future, goes through this one path.
const installs = await client.invoke("marketplace.install.list", {});

const subscription = await client.invoke("webhooks.subscription.create", {
  topic: "hosting.server.crashed",
  url: "https://ops.example.com/hooks/umbrella-crash-alert",
});
```

### Auth

Only `X-Api-Key` (a scoped key from the `identity.apikey.create`
capability) is supported by this SDK. Session-cookie and admin-key auth
exist server-side (`api/middleware/api_key_auth.py`) but are for the
dashboard and bootstrap/CLI use respectively — an external consumer of
this package should always be using a real scoped key. See
`src/client.ts`'s `UmbrellaClientOptions` docstring for the
`discordUserId` delegate option, if your key carries
`identity.discord_delegate`.

### Error handling

A non-2xx response throws `UmbrellaApiError` (`status`, `body`):

```typescript
import { UmbrellaApiError } from "@umbrellaos/sdk";

try {
  await client.invoke("marketplace.install.install", { plugin_id: "x", version: "1.0.0" });
} catch (err) {
  if (err instanceof UmbrellaApiError) {
    console.error(err.status, err.body);
  }
}
```

## Why a thin wrapper instead of a full generated client

`openapi-typescript` (types only) + a hand-written `UmbrellaClient`
class, not `openapi-generator-cli`'s `typescript-fetch` target (a fuller
generated client with one method per endpoint). Reasoning, stated
plainly:

UmbrellaOS's entire public REST surface is exactly two routes —
`GET /api/v1/capabilities` and `POST /api/v1/capabilities/{name}/invoke`
(see `registry/adapters/rest.py`'s own module docstring in
umbrella-core: "This single route is the entire REST surface for every
current and future capability"). A full generator would produce one
generated method per *capability name* (there are ~90 today, and that
number only grows), each one just a differently-named wrapper around the
same `POST .../invoke` call with a string literal baked in — more
generated surface to keep in sync on every schema regen, not less risk,
for an API that doesn't actually have per-endpoint variation to
generate against.

`openapi-typescript`'s output (`src/generated-types.ts`) already gives
real compile-time types for `CapabilitySummary` and the invoke
request/response shape — genuinely useful, kept. `src/client.ts` is the
part a generator can't produce on its own: knowing which header carries
auth, when to send `X-Discord-User-Id`, and how a 401 vs. a 422 vs. a
capability's own error shape should surface to the caller.

If UmbrellaOS's REST surface ever grows real resource-styled route
aliases on top of the generic invoke path (`registry/adapters/rest.py`'s
own docstring mentions this as a deferred, not abandoned, possibility),
revisit this decision then — a full generator makes much more sense
against a REST surface that actually has per-resource routes to
generate.

## Verification

- `npm run typecheck` and `npm run build`: clean.
- `scripts/integration-test.mjs`: a real integration test against a
  live local backend (SQLite-backed `uvicorn main:app`, not mocked) —
  exercises `listCapabilities()`, a read-only `invoke()` call, a full
  create/list/delete round-trip against `webhooks.subscription.*`
  (proving params, a server-generated id, and multi-call sequencing all
  work), and confirms an invalid capability name raises a structured
  `UmbrellaApiError`. All passed — see the handback doc for the full
  run transcript. Not part of `npm run typecheck`/`build`; run manually
  against a locally-booted backend:

  ```bash
  # from umbrella-core-CURRENT, in a fresh venv, with a local Postgres/SQLite + redis:
  ```
